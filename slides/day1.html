Docker refresher

Image and container

writable layercontainer only, gone on delete
app filesCOPY --from=build /out .
ASP.NET Core runtimemcr.microsoft.com/dotnet/aspnet:10.0
Debian baseOS files, no kernel
  • An image is read-only layers plus metadata: entrypoint, ports, user.
  • A container is a process started from an image, with one thin writable layer on top.
  • A tag (:v1) is a movable name. The digest (sha256:…) never changes.
  • A registry stores images. Ours is ghcr.io/amirilovic/k8s-training-app.
  • Point out the writable layer: anything the app writes to disk is lost when the container is removed. That comes back on Wednesday with Postgres.

The training app's Dockerfile

# build stage: SDK image compiles the app
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY TrainingApp.csproj .
RUN dotnet restore
COPY . .
RUN dotnet publish -c Release -o /out

# runtime stage: only the runtime and the output
FROM mcr.microsoft.com/dotnet/aspnet:10.0
WORKDIR /app
COPY --from=build /out .
USER $APP_UID
ENTRYPOINT ["dotnet", "TrainingApp.dll"]
  • Two stages: the SDK never ships.
  • Restore before copying the source, so the package layer is cached.
  • .NET 8 and later images listen on 8080, not 80.
  • USER $APP_UID runs as the non-root app user.
  • The real file in app/Dockerfile also handles multi-architecture builds (TARGETARCH) and bakes the version in. Simplified here.
  • Port 8080 is the first bug people hit when they copy an old manifest with port 80.

What Docker gives us, and what it doesn't

Docker gives us

  • One package with the app, the runtime and the OS files.
  • The same image on a laptop, in CI and in production.
  • Isolation: own filesystem, own processes, own ports.
  • A registry to store versions and pull them anywhere.
  • Fast start, in seconds instead of a VM's minutes.

Docker doesn't give us

  • Running one service on many machines.
  • Load balancing requests between containers.
  • Releases without downtime, and rollback.
  • Configuration per environment, outside the image.
  • Automatic horizontal scaling when load goes up.
  • Ask the room for the left column first, then the right. Docker's restart policy exists, but only on the same machine.

What Kubernetes is

Kubernetes is a container orchestration platform

It runs containerized services across a group of machines (a cluster) and keeps them running the way you described them.

  • High availability: failed containers restart, and copies spread over several machines.
  • Scaling up and down, by hand or automatically with load.
  • Releases without downtime, and rollback.
  • Service discovery and load balancing between copies.
  • Configuration and secrets kept outside the image.
  • One way to deploy every service, on a laptop, in AWS or in Azure.
  • Tie it back to the Docker slide: every bullet here answers one item from the "Docker doesn't give us" column.

Inside the cluster

Click a box or a zone name to see what it does.

Control plane

The machines that run the cluster itself. Here it is one Docker container, training-control-plane. It has a taint, so your pods never land on it. On EKS and AKS you never see it: the cloud provider runs it for you.

kubectl describe node training-control-plane | grep Taints

API server

The front door of the cluster. kubectl, the scheduler, the controllers and every kubelet talk only to the API server. It checks who you are and what you may do, validates the object, stores it in etcd, and tells everyone watching that something changed.

kubectl get pods -n kube-system -l component=kube-apiserver

etcd

A key-value database with every object in the cluster: Deployments, pods, Secrets and their status. Only the API server reads and writes it. Lose etcd without a backup and the cluster forgets everything it was managing. On EKS and AKS the cloud provider runs and backs it up.

kubectl get pods -n kube-system -l component=etcd

Scheduler

Watches for new pods that have no node yet, picks one and writes it into the pod. It skips nodes without enough free CPU and memory for the pod's requests, then prefers the best fit. It starts nothing itself. A pod that fits nowhere stays Pending.

kubectl get pods -n kube-system -l component=kube-scheduler

Controller manager

Runs the control loops, one per kind of object. The ReplicaSet controller keeps the pod count, the Deployment controller runs rollouts, the node controller notices dead nodes. Each loop compares what you asked for with what exists and fixes the difference.

kubectl get pods -n kube-system -l component=kube-controller-manager

Node

A machine that runs your pods: a VM or a physical server, here a Docker container. Every node runs a kubelet, a container runtime and kube-proxy, which routes Service traffic (Tuesday). More nodes means more room for pods.

kubectl get nodes -o wide

kubelet

The agent on every node. It watches the API server for pods assigned to its node, asks containerd to start their containers, restarts crashed containers and reports pod status back. It is a system service on the node, not a pod.

docker exec training-worker systemctl status kubelet

containerd

The container runtime. It pulls images and starts and stops containers when the kubelet asks. Docker uses containerd underneath too, so an image built with docker build runs here unchanged. Kubernetes does not need Docker on its nodes.

docker exec training-worker crictl ps

Pod

The smallest thing Kubernetes runs: one or more containers that share an IP address and volumes and always land on the same node. Usually one app container per pod. Pods are replaced, not repaired: a new pod gets a new name and a new IP. You can think of it like a virtual machine running containers.

kubectl get pods -A -o wide
  • Click each part while you explain it. The panel shows a command for each one; run it live on your cluster.
  • kubectl only ever talks to the API server. Nothing talks to etcd directly.
  • In Lab 1 they find these components as pods in kube-system.

How do we talk to Kubernetes?

kubectl config use-context kind-training
Switched to context "kind-training".

kubectl run hello \

NAME    READY   STATUS    RESTARTS   AGE

  • kubectl is the command-line client. Every command is an HTTPS request to the API server.
  • ~/.kube/config says which cluster and which user. That pair is a context.
  • use-context switches cluster. kubectl config current-context shows where you are.
  • Run it live, then once more with -v=6 and point at the request line: POST https://127.0.0.1:…/api/v1/namespaces/default/pods, 201 Created. That proves the first bullet. The URL also previews the manifest slide: /api/v1 is apiVersion: v1, namespaces/default is the namespace, pods is the kind.
  • kind create cluster switches the context to kind-training. Anyone with work clusters in their kubeconfig should check current-context before deleting anything.
  • k9s, Lens, Helm and CI pipelines all talk to the same API. kubectl is just the client everyone has.
  • Leave the hello pod running: the next slide reads it back.

Every object has the same shape

$ kubectl get pod hello -o yaml

statusWhat is. Kubernetes writes it.

Kubernetes filled in defaults, the scheduler's choice and status. A file you write needs only the first four fields.

  • Run kubectl get pod hello -o yaml live. The real output is several screens long; the slide keeps the parts worth pointing at.
  • kubectl run added the label run: hello. nodeName is the scheduler's decision from the cluster diagram, and status comes from the kubelet.
  • The next slide shows who fills in nodeName and status: the scheduler and the kubelet, step by step.
  • Nobody writes this from memory. In Lab 1 they generate a file with kubectl run web --image=... --dry-run=client -o yaml.
  • Delete the pod afterwards: kubectl delete pod hello.

Namespaces

  • A namespace is a folder for objects. Names must be unique inside one, not across.
  • kube-system holds the cluster's own parts. You will find the API server there.
  • Every command works in one namespace. -n picks another, -A means all.
  • Today everyone switches to training, so you can leave out -n.
kubectl get namespaces
kubectl get pods -n kube-system
kubectl get pods -A

kubectl create namespace training
kubectl config set-context --current \
  --namespace training

Companies usually give each business domain or each team its own namespace: payments, orders, search, or team-checkout, team-platform. When one cluster serves several environments, they add a suffix: payments-dev, payments-prod.

Labels, ReplicaSets, Deployments

Labels and selectors

selector: app=web
↓ matches
podapp=web
podapp=web
podapp=postgres
kubectl label pod <pod> env=dev
kubectl get pods --show-labels
kubectl get pods -l app=web
  • Labels are key-value tags on any object.
  • A selector is a query over labels. Deployments and Services find their pods this way, not by name.
  • Change a pod's label and it leaves its Deployment. The Deployment then creates a replacement.
  • Demo if time: add a label to any pod, then list labels and filter with -l.
  • Changing a label that already exists needs --overwrite, for example kubectl label pod <pod> env=prod --overwrite.
  • kubectl label pod <pod> env- removes the label.

  • A Deployment runs your app as a set of identical pods. It keeps their number and replaces them step by step on each release.
  • You write the Deployment. You never write the ReplicaSet.
  • The ReplicaSet keeps the count. The Deployment manages versions.
  • The hash in the name changes when the pod template changes.

You describe the result, controllers do the work

→

→

→
actual state3 running
↺
  • You never say "start a container". You say "there should be 3", and a loop keeps it true.
  • The loop runs forever. A pod that dies at 3 a.m. is replaced the same way as one you delete now.
  • Every kind of object (Deployment, Service, Job) has its own controller.

A Deployment in YAML

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:                # the pod to create
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: ghcr.io/amirilovic/k8s-training-app:v1
          ports:
            - containerPort: 8080
replicasHow many pods. The ReplicaSet keeps this count.
selectorWhich pods belong to it. Must match the template's labels.
templateThe pod to create: the Pod manifest from before, without apiVersion and kind.
kubectl apply -f deployment.yaml

Change the image and apply again: that is a release.

  • This is the file they write in Lab 2, labs/02-deployments.
  • Point at the two app: web labels. If selector and template labels differ, the API server rejects the Deployment.
  • apply creates the object the first time and updates it after that. The rolling update slide shows what an update does.

A rolling update, step by step

A rolling update deploys a new version of the service without downtime. It replaces pods a few at a time: start a new one, wait until it runs, remove an old one.

StepOld (v1)New (v2)
start● ● ●
1● ● ●○ starting
2● ●●
3● ●● ○
…●● ●
done● ● ●

Two settings set the pace. maxSurge is how many extra pods may exist during the update, and maxUnavailable is how many may be missing.

Both default to 25%: with 3 replicas that is 1 extra and 0 missing, so there are always at least 3 pods.

The old ReplicaSet stays, scaled to 0, so a rollback is instant.

Rollout commands

kubectl set image deployment/web web=…:v2Give container web a new image. That starts a rollout.
kubectl rollout status deployment/webWait until the rollout is done, or see where it is stuck.
kubectl rollout history deployment/webList the revisions. Each one is a ReplicaSet.
kubectl rollout undo deployment/webGo back one revision, not to the first one.
kubectl rollout undo deployment/web --to-revision=1Go back to a chosen revision.

In real projects you change the image tag in the YAML file and apply it. set image is a shortcut for the lab.

Never deploy :latest. A rollback needs a tag that still points at the old image.
