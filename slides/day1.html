Docker refresher

Image and container

writable layercontainer only, gone on delete
app filesCOPY --from=build /out .
ASP.NET Core runtimemcr.microsoft.com/dotnet/aspnet:10.0
Debian baseOS files, no kernel
  • An image is read-only layers plus metadata: entrypoint, ports, user.
  • A container is a process started from an image, with one thin writable layer on top.
  • A tag (:v1) is a movable name. The digest (sha256:…) never changes.
  • A registry stores images. Ours is ghcr.io/amirilovic/k8s-training-app.
  • Point out the writable layer: anything the app writes to disk is lost when the container is removed. That comes back on Wednesday with Postgres.

The training app's Dockerfile

# build stage: SDK image compiles the app
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY TrainingApp.csproj .
RUN dotnet restore
COPY . .
RUN dotnet publish -c Release -o /out

# runtime stage: only the runtime and the output
FROM mcr.microsoft.com/dotnet/aspnet:10.0
WORKDIR /app
COPY --from=build /out .
USER $APP_UID
ENTRYPOINT ["dotnet", "TrainingApp.dll"]
  • Two stages: the SDK never ships.
  • Restore before copying the source, so the package layer is cached.
  • .NET 8 and later images listen on 8080, not 80.
  • USER $APP_UID runs as the non-root app user.
  • The real file in app/Dockerfile also handles multi-architecture builds (TARGETARCH) and bakes the version in. Simplified here.
  • Port 8080 is the first bug people hit when they copy an old manifest with port 80.

What Docker gives us, and what it doesn't

Docker gives us

  • One package with the app, the runtime and the OS files.
  • The same image on a laptop, in CI and in production.
  • Isolation: own filesystem, own processes, own ports.
  • A registry to store versions and pull them anywhere.
  • Fast start, in seconds instead of a VM's minutes.

Docker doesn't give us

  • Running one service on many machines.
  • Load balancing requests between containers.
  • Releases without downtime, and rollback.
  • Configuration per environment, outside the image.
  • Automatic horizontal scaling when load goes up.

The right column is what Kubernetes adds, and it is the map of the three days: Deployments today, Services and config tomorrow, autoscaling on Wednesday.

  • Ask the room for the left column first, then the right. Docker's restart policy exists, but only on the same machine.

Running
  • apply returns as soon as the object is stored. The pod starts afterwards.
  • Each step writes back to the object's status. That is what kubectl get and describe show you.
  • When something hangs, the last step that succeeded tells you where to look.

Every object has the same shape

Namespaces

  • A namespace is a folder for objects. Names must be unique inside one, not across.
  • kube-system holds the cluster's own parts. You will find the API server there.
  • Every command works in one namespace. -n picks another, -A means all.
  • Today everyone switches to training, so you can leave out -n.
kubectl get namespaces
kubectl get pods -n kube-system
kubectl get pods -A

kubectl create namespace training
kubectl config set-context --current \
  --namespace training

Labels, ReplicaSets, Deployments

Labels and selectors

selector: app=web
↓ matches
podapp=web
podapp=web
podapp=postgres
  • Labels are key-value tags on any object.
  • A selector is a query over labels. Deployments and Services find their pods this way, not by name.
  • Change a pod's label and it leaves its Deployment. The Deployment then creates a replacement.
  • Demo if time: kubectl get pods --show-labels, then kubectl get pods -l app=web.

Kubernetes cannot see inside your app

Without a readiness probe, a new pod counts as ready as soon as its container starts.

Our app waits 3 seconds before it listens. Kubernetes sends it traffic anyway.

A broken release (v3-broken exits on startup) passes this test too, for a moment. In Lab 2 it replaces every healthy pod.

Rollout commands

kubectl set image deployment/web \
  web=ghcr.io/amirilovic/k8s-training-app:v2
kubectl rollout status deployment/web
kubectl rollout history deployment/web

kubectl rollout undo deployment/web
kubectl rollout undo deployment/web --to-revision=1
  • undo goes back one revision, not to the first one.
  • In real projects you change the image tag in YAML and apply. set image is for the lab.
  • Never deploy :latest. You cannot roll back to "the previous latest".

.NET: stopping cleanly

pod marked for deletion
→
SIGTERM.NET host starts shutdown
→
in-flight requests finishHostOptions.ShutdownTimeout
→
SIGKILLafter 30 s grace period
  • The generic host handles SIGTERM for you. Look for "SIGTERM received" in the training app's logs.
  • Both timeouts default to 30 seconds in .NET 8 and later. Keep the host's shorter than terminationGracePeriodSeconds.
  • Long background work needs stoppingToken checks, or it is killed halfway.
