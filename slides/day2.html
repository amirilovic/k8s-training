Services and DNS

Pods come and go. Their IPs too.

kubectl get pods -o wide

NAME              IP            NODE
web-848b…-cg4bh   10.244.1.7    training-worker
web-848b…-8cmwj   10.244.2.4    training-worker2
web-848b…-b54cp   10.244.1.9    training-worker

kubectl delete pod web-848b…-cg4bh
web-848b…-q2lzx   10.244.2.11   training-worker2
  • Every pod gets its own IP, and a new one when it is replaced.
  • Hard-coding pod IPs breaks on the next rollout.
  • A Service gives a group of pods one name and one IP that never change.

A Service finds pods by label

Service web10.96.198.9 · port 80
→
EndpointSliceready pods only
→
10.244.1.7:8080app=web · ready
10.244.2.4:8080app=web · ready
10.244.1.9:8080app=web · not ready
  • The selector app: web must match the pod labels exactly. A typo gives a Service with no endpoints and no error.
  • Only ready pods receive traffic. That is how readiness probes, later today, keep traffic away from a starting pod.

Service types

TypeReachable fromUsed for
ClusterIPinside the cluster onlyapps calling each other. The default.
NodePortevery node, on a port 30000–32767reaching an app from outside without a cloud. Our labs use it.
LoadBalancera cloud load balancer in front of the nodesa public address in AWS or Azure, mostly for TCP and UDP traffic. HTTP usually goes through an Ingress.

In real clusters, almost every app has a ClusterIP Service. Traffic from outside comes in through an Ingress, the next talk.

  • The Ingress controller is itself a Service: LoadBalancer in the cloud, NodePort 30081 in our kind cluster. That is the only Service exposed to the outside.

From your browser to a pod

Windows browserlocalhost:30080
→
kind node containerport 30080, from kind.yaml
→
Service webnodePort 30080 · port 80
→
podtargetPort 8080
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: NodePort
  selector:
    app: web
  ports:
    - port: 80          # http://web
      targetPort: 8080  # the container
      nodePort: 30080   # the node
  • Three port numbers, three different things. Most Service bugs are one of them.
  • targetPort: 80 on a .NET 8 app gives "connection refused".

Cluster DNS

From a pod inName that works
the same namespacehttp://web
another namespacehttp://web.training
anywhere, fullyweb.training.svc.cluster.local
  • In appsettings.json a dependency is just http://orders, and the same file works in every namespace.
  • A Service balances connections, not requests. A browser keeps its connection open and often stays on one pod.
  • The connection point matters for .NET: HttpClient pools connections, so one client instance can stick to one pod for a long time. SocketsHttpHandler.PooledConnectionLifetime helps spread load.

No proxy: the node rewrites the address

calling podweb.training → 10.96.198.9:80
→
iptables on its node10.96.198.9:80 → 10.244.2.4:8080
→
web pod10.244.2.4:8080, any node
  • The ClusterIP belongs to no machine. kube-proxy on every node writes iptables rules that recognise it.
  • On the caller's node, the rules pick a ready pod at random and rewrite the destination to its IP. The kernel keeps that choice for the whole connection.
  • Then it is ordinary routing: to a pod on the same node, or to the node that owns that pod's IP range.
  • Replies are rewritten back, so the caller only ever sees the ClusterIP.
  • Show the rules live: docker exec training-worker iptables-save -t nat | grep training/web. Each pod gets a line with "statistic --mode random --probability", then a DNAT line with its IP.
  • docker exec training-worker ip route shows one route per local pod and one per other node's pod range (10.244.x.0/24 via that node's IP).
  • This is why a Service balances connections, not requests: the random pick happens once, when the connection opens.
  • Other kube-proxy modes (IPVS, nftables) and eBPF-based CNIs like Cilium do the same job with a different kernel mechanism.

Ingress

One entry point, routed by host and path

browserapp.localhost:30081
→
Traefikingress controller, NodePort 30081
→
Service webhost app.localhost
Service web-v2host v2.localhost
→
pods
  • An Ingress is a set of routing rules. It does nothing without a controller that reads it.
  • Apps keep ClusterIP Services. Only the controller is exposed.
  • Chrome and Edge send any *.localhost name to your own machine, so no hosts file edits.

An Ingress in YAML

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
spec:
  ingressClassName: traefik
  rules:
    - host: app.localhost
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web
                port: { number: 80 }

ingressClassName picks the controller. Older charts use an annotation instead:

metadata:
  annotations:
    kubernetes.io/ingress.class: alb

Many existing Ingresses still use the annotation, for example with AWS ALB or Traefik as the controller.

Controllers differ in the annotations

annotations:
  alb.ingress.kubernetes.io/scheme: internal
  alb.ingress.kubernetes.io/target-type: ip
  alb.ingress.kubernetes.io/healthcheck-path: /readyz
  alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:…
  • The Ingress spec only covers hosts, paths and TLS.
  • Everything else (health checks, certificates, auth) is an annotation that one controller understands.
  • That is why Ingress files look different in every company.

.NET behind a proxy

Behind Traefik or an ALB, ASP.NET Core sees the proxy's address and http, even when the browser used HTTPS.

Redirects, generated links and OAuth callbacks then point to the wrong place.

env:
  - name: ASPNETCORE_FORWARDEDHEADERS_ENABLED
    value: "true"

This makes ASP.NET Core read the X-Forwarded-For and X-Forwarded-Proto headers the proxy adds.

Configuration

One image, every environment

  • The same v1 image runs in dev and prod. Only configuration differs.
  • Configuration lives in the cluster, next to the Deployment that uses it.
  • Change a setting without building a new image.
ObjectHolds
ConfigMapsettings, whole files like appsettings.json
Secretpasswords, keys, connection strings

A ConfigMap in YAML

apiVersion: v1
kind: ConfigMap
metadata:
  name: web-config
data:
  appsettings.json: |
    {
      "Greeting": {
        "Text": "Hello from a ConfigMap"
      }
    }
dataKeys and values. A value can be a whole file.
|Keeps the lines below exactly as written.
mountedEach key becomes a file: /config/appsettings.json.
kubectl create configmap web-config \
  --from-file=appsettings.json \
  --dry-run=client -o yaml
  • No spec and no status: a ConfigMap is data, nothing runs.
  • The same dry-run trick as yesterday, this time with --from-file. Lab 5 generates this file that way.

A Secret in YAML

apiVersion: v1
kind: Secret
metadata:
  name: web-secrets
type: Opaque
data:
  Secrets__ApiKey: dHJhaW5pbmctYXBpLWtleS0xMjM0
kubectl create secret generic web-secrets \
  --from-literal=Secrets__ApiKey=training-api-key-1234 \
  --dry-run=client -o yaml
typeOpaque means any keys you like. Other types hold TLS certificates or registry logins.
dataValues are base64, not encrypted. base64 -d reads them.
stringDataWrite plain text instead. Kubernetes encodes it for you.
  • Decode it live: echo dHJhaW5pbmctYXBpLWtleS0xMjM0 | base64 -d prints training-api-key-1234.
  • Never commit a real Secret to git. In production the values come from a secret store, covered on "Two things that surprise .NET developers".

How it reaches .NET configuration

command-line argshighest priority
environment variablesenv: Greeting__Text
/secrets/Secrets__ApiKeySecret mounted as files, AddKeyPerFile
/config/appsettings.jsonConfigMap mounted as a file
appsettings.json in the imagelowest priority
  • Later providers win. That is why an env var beats the mounted file.
  • __ in a name becomes :. Greeting__Text is Greeting:Text.
  • Your code reads IConfiguration as always. It does not know about Kubernetes.
  • This is the training app's actual provider order, see app/Program.cs. In a default ASP.NET Core app you add the /config and /secrets providers yourself.

Mounting a ConfigMap and a Secret

    spec:
      containers:
        - name: web
          env:
            - name: Greeting__Text
              value: "Hello from an env var"
          volumeMounts:
            - name: config
              mountPath: /config
            - name: secrets
              mountPath: /secrets
      volumes:
        - name: config
          configMap:
            name: web-config
        - name: secrets
          secret:
            secretName: web-secrets
  • Each key in the ConfigMap or Secret becomes one file in the folder.
  • Env vars are fixed when the container starts.
  • Mounted files are updated in place, within about a minute. The app still has to reload them.

Two things that surprise .NET developers

reloadOnChange misses updates

Kubernetes swaps a symlink instead of writing the file. FileSystemWatcher never fires. In the lab the file changes and the app keeps the old value.

Fix: DOTNET_USE_POLLING_FILE_WATCHER=true, or restart the pods.

Secrets are not encrypted

Values are base64. kubectl get secret -o yaml plus base64 -d shows them to anyone allowed to read Secrets.

In production they come from a secret store (Vault, AWS Secrets Manager) and access is limited with RBAC.

Probes

Kubernetes cannot see inside your app

Without a readiness probe, a new pod counts as ready as soon as its container starts.

Our app waits 3 seconds before it listens. Kubernetes sends it traffic anyway.

A broken release (v3-broken exits on startup) passes this test too, for a moment. In Lab 2 it replaced every healthy pod.

9
failed requests out of 339 during a rollout from v1 to v2, no probes
  • Measured on kind with a curl loop every 100 ms. They count their own failures in step 1 of Lab 6.
  • The last slide of this talk shows the same rollout with probes: 0 failures.

Three probes, three different reactions

ProbeQuestionWhen it fails
readinessProbeCan it take traffic now?pod leaves the Service, no restart
livenessProbeIs it stuck for good?container is restarted
startupProbeHas it finished starting?holds off the other two until it passes
  • Readiness also gates rollouts: the next old pod goes only when a new one is ready.
  • A wrong liveness probe turns a slow database into a restart loop across every pod.

Probe settings and their defaults

timeoutSeconds1How long one check may take
periodSeconds10How often it checks
failureThreshold3Failures in a row before it counts as failed
successThreshold1Successes in a row to pass again. Must be 1 for liveness and startup.
initialDelaySeconds0Wait after the container starts before the first check
  • The same defaults for all three probes.
  • A broken pod is noticed after about 30 s: 3 failures, 10 s apart.
  • Give a startup probe more room, for example failureThreshold: 30.
  • The 1-second timeout is the common trap: a /readyz that checks a slow database, or the first request after startup while .NET compiles code, takes longer and the pod flips between ready and not ready. Set timeoutSeconds to 2 to 5 when a check calls a dependency, and keep the check cheap.
  • Lab 6 sets periodSeconds: 5 and failureThreshold: 2 for readiness, so a pod leaves the Service about 10 s after /readyz starts failing.
  • startupProbe with failureThreshold: 30 and periodSeconds: 2 gives about 60 s to start; liveness keeps its own, quicker settings afterwards.

.NET health checks map onto probes

builder.Services.AddHealthChecks()
    .AddCheck("alive", ..., tags: ["live"])
    .AddCheck<DatabaseHealthCheck>(
        "database", tags: ["ready"]);

app.MapHealthChecks("/healthz",
    new() { Predicate = c => c.Tags.Contains("live") });
app.MapHealthChecks("/readyz",
    new() { Predicate = c => c.Tags.Contains("ready") });
livenessProbe:
  httpGet: { path: /healthz, port: 8080 }
readinessProbe:
  httpGet: { path: /readyz, port: 8080 }

The database check is tagged for readiness only. If Postgres goes down, pods stop getting traffic, but nothing restarts.

The same rollout, with probes

9
failed of 339 requests, v1 to v2, no probes
0
failed of 366 requests, with a readiness probe and a 5 s preStop pause
  • The readiness probe keeps traffic away until the app listens.
  • The preStop sleep keeps an old pod serving while the Service drops it from its endpoints.
  • Both numbers measured on kind with the training app. The preStop pause covers the gap between the pod being marked for deletion and every node updating its routing.
  • Lab 6's extra repeats v3-broken with probes: the rollout stops at one crashing pod and the old pods keep serving.

.NET: stopping cleanly

pod marked for deletionpreStop pause runs first
→
SIGTERM.NET host starts shutdown
→
in-flight requests finishHostOptions.ShutdownTimeout
→
SIGKILLafter 30 s grace period
  • The generic host handles SIGTERM for you. Look for "SIGTERM received" in the training app's logs.
  • Everything must fit in terminationGracePeriodSeconds, 30 s by default: the preStop pause plus the .NET shutdown. .NET 8 also waits up to 30 s, so with a 5 s pause set HostOptions.ShutdownTimeout below 25 s.
  • Long background work needs stoppingToken checks, or it is killed halfway.
