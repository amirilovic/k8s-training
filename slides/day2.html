Services and DNS

Pods come and go. Their IPs too.

kubectl get pods -o wide

NAME              IP            NODE
web-848b…-cg4bh   10.244.1.7    training-worker
web-848b…-8cmwj   10.244.2.4    training-worker2
web-848b…-b54cp   10.244.1.9    training-worker

kubectl delete pod web-848b…-cg4bh
web-848b…-q2lzx   10.244.2.11   training-worker2
  • Every pod gets its own IP, and a new one when it is replaced.
  • Hard-coding pod IPs breaks on the next rollout.
  • A Service gives a group of pods one name and one IP that never change.

A Service finds pods by label

Service web10.96.198.9 · port 80
→
EndpointSliceready pods only
→
10.244.1.7:8080app=web · ready
10.244.2.4:8080app=web · ready
10.244.1.9:8080app=web · not ready
  • The selector app: web must match the pod labels exactly. A typo gives a Service with no endpoints and no error.
  • Only ready pods receive traffic. That is how readiness probes, later today, keep traffic away from a starting pod.

Service types

In real clusters, apps use ClusterIP and outside traffic comes in through an Ingress, the next talk. NodePort is the shortcut to your browser.

  • In appsettings.json a dependency is just http://orders, and the same file works in every namespace.
  • A Service balances connections, not requests. A browser keeps its connection open and often stays on one pod.
  • The connection point matters for .NET: HttpClient pools connections, so one client instance can stick to one pod for a long time. SocketsHttpHandler.PooledConnectionLifetime helps spread load.
10 minutes · talk

Ingress

One entry point, routed by host and path

browserapp.localhost:30081
→
Traefikingress controller, NodePort 30081
→
Service webhost app.localhost
Service web-v2host v2.localhost
→
pods
  • An Ingress is a set of routing rules. It does nothing without a controller that reads it.
  • Apps keep ClusterIP Services. Only the controller is exposed.
  • Chrome and Edge send any *.localhost name to your own machine, so no hosts file edits.

An Ingress in YAML

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
spec:
  ingressClassName: traefik
  rules:
    - host: app.localhost
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web
                port: { number: 80 }

ingressClassName picks the controller. Older charts use an annotation instead:

metadata:
  annotations:
    kubernetes.io/ingress.class: alb

Most Ingresses in Epic's clusters still use the annotation, with AWS ALB or Traefik as the controller.

Controllers differ in the annotations

annotations:
  alb.ingress.kubernetes.io/scheme: internal
  alb.ingress.kubernetes.io/target-type: ip
  alb.ingress.kubernetes.io/healthcheck-path: /readyz
  alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:…
  • The Ingress spec only covers hosts, paths and TLS.
  • Everything else (health checks, certificates, auth) is an annotation that one controller understands.
  • That is why Ingress files look different in every company.

.NET behind a proxy

Behind Traefik or an ALB, ASP.NET Core sees the proxy's address and http, even when the browser used HTTPS.

Redirects, generated links and OAuth callbacks then point to the wrong place.

env:
  - name: ASPNETCORE_FORWARDEDHEADERS_ENABLED
    value: "true"

This makes ASP.NET Core read the X-Forwarded-For and X-Forwarded-Proto headers the proxy adds.

Configuration

One image, every environment

  • The same v1 image runs in dev and prod. Only configuration differs.
  • Configuration lives in the cluster, next to the Deployment that uses it.
  • Change a setting without building a new image.
ObjectHolds
ConfigMapsettings, whole files like appsettings.json
Secretpasswords, keys, connection strings

How it reaches .NET configuration

command-line argshighest priority
environment variablesenv: Greeting__Text
/secrets/Secrets__ApiKeySecret mounted as files, AddKeyPerFile
/config/appsettings.jsonConfigMap mounted as a file
appsettings.json in the imagelowest priority
  • Later providers win. That is why an env var beats the mounted file.
  • __ in a name becomes :. Greeting__Text is Greeting:Text.
  • Your code reads IConfiguration as always. It does not know about Kubernetes.
  • This is the training app's actual provider order, see app/Program.cs. In a default ASP.NET Core app you add the /config and /secrets providers yourself.

Mounting a ConfigMap and a Secret

    spec:
      containers:
        - name: web
          env:
            - name: Greeting__Text
              value: "Hello from an env var"
          volumeMounts:
            - name: config
              mountPath: /config
            - name: secrets
              mountPath: /secrets
      volumes:
        - name: config
          configMap:
            name: web-config
        - name: secrets
          secret:
            secretName: web-secrets
  • Each key in the ConfigMap or Secret becomes one file in the folder.
  • Env vars are fixed when the container starts.
  • Mounted files are updated in place, within about a minute. The app still has to reload them.

Two things that surprise .NET developers

reloadOnChange misses updates

Kubernetes swaps a symlink instead of writing the file. FileSystemWatcher never fires. In the lab the file changes and the app keeps the old value.

Fix: DOTNET_USE_POLLING_FILE_WATCHER=true, or restart the pods.

Secrets are not encrypted

Values are base64. kubectl get secret -o yaml plus base64 -d shows them to anyone allowed to read Secrets.

In production they come from a secret store (Vault, AWS Secrets Manager) and access is limited with RBAC.

Probes

Three probes, three different reactions

ProbeQuestionWhen it fails
readinessProbeCan it take traffic now?pod leaves the Service, no restart
livenessProbeIs it stuck for good?container is restarted
startupProbeHas it finished starting?holds off the other two until it passes
  • Readiness also gates rollouts: the next old pod goes only when a new one is ready.
  • A wrong liveness probe turns a slow database into a restart loop across every pod.

.NET health checks map onto probes

builder.Services.AddHealthChecks()
    .AddCheck("alive", ..., tags: ["live"])
    .AddCheck<DatabaseHealthCheck>(
        "database", tags: ["ready"]);

app.MapHealthChecks("/healthz",
    new() { Predicate = c => c.Tags.Contains("live") });
app.MapHealthChecks("/readyz",
    new() { Predicate = c => c.Tags.Contains("ready") });
livenessProbe:
  httpGet: { path: /healthz, port: 8080 }
readinessProbe:
  httpGet: { path: /readyz, port: 8080 }

The database check is tagged for readiness only. If Postgres goes down, pods stop getting traffic, but nothing restarts.

The same rollout, with probes

9
failed of 339 requests, v1 to v2, no probes (Monday)
0
failed of 366 requests, with a readiness probe and a 5 s preStop pause
  • The readiness probe keeps traffic away until the app listens.
  • The preStop sleep keeps an old pod serving while the Service drops it from its endpoints.
  • Both numbers measured on kind with the training app. The preStop pause covers the gap between the pod being marked for deletion and every node updating its routing.
  • Lab 6's extra repeats v3-broken with probes: the rollout stops at one crashing pod and the old pods keep serving.
