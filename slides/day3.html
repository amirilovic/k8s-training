Requests and limits

Requests and limits

Requests tell Kubernetes how much CPU and memory a container needs, so it lands on a node with room. Limits are the most it may use.

resources:
  requests:          # reserved, used for scheduling
    cpu: 100m        # 0.1 of a core
    memory: 128Mi
  limits:            # hard ceiling
    cpu: "1"
    memory: 256Mi
Over the limitWhat happens
CPUthrottled, gets slower
memorykilled: OOMKilled exit 137
request too big for any nodePending forever

.NET reads the limits

Container setting.NET sees
CPU limit 1Environment.ProcessorCount = 1
memory limit 128MiGC heap limit 96 MB (75%)

/admin/leak?managed=true fills byte[] until .NET throws OutOfMemoryException. The container survives.

/admin/leak fills native memory, which the GC does not limit. Linux kills the container: OOMKilled

Thread pool and Server GC size themselves from ProcessorCount, so a CPU limit changes how your app behaves under load.

  • Numbers from /api/info on kind with a 128Mi limit and a CPU limit of 1.
  • Native leaks in real apps: unmanaged libraries, image processing, large pinned buffers.

Autoscaling

The HorizontalPodAutoscaler

A way to set how many replicas a Deployment runs based on the application's load.

kubeletmeasures pods
→
metrics-serverkubectl top
→
HPAevery 15 s
→
Deploymentreplicas: 2 … 6
  • Every 15 seconds the HPA reads the pods' CPU use from metrics-server and works out how many replicas are needed.
  • The HPA only changes one number: the Deployment's replicas.
  • It adds pods, not nodes. When nodes are full, new pods stay Pending. The cluster autoscaler adds nodes, and that is a platform job.

An HPA in YAML

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 2
  maxReplicas: 6
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 50 }
    - type: Resource
      resource:
        name: memory
        target: { type: Utilization, averageUtilization: 80 }
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 30
  • averageUtilization: 50 is the target percentage, averaged over all the Deployment's pods. One pod at 90% and one at 10% average to 50%, which counts as on target.
  • stabilizationWindowSeconds: before removing pods, the HPA takes its highest recommendation from this window, so a short dip removes nothing.
  • Default 300 s down, 0 s up. The lab uses 30 s.
  • With two metrics the HPA works out a replica count for each and uses the higher one. Memory needs a memory request, and it is a weak signal for .NET: the GC keeps memory after a burst, so memory-based scaling adds pods but rarely removes them. Use it as a safety net with a high target.
  • Remove replicas from the Deployment once an HPA owns it, or every kubectl apply resets the count until the HPA corrects it. Lab 7 has this as a "Finished early?" extra.

How it decides

utilization = CPU used ÷ CPU request

desired = ceil( current × utilization ÷ target )
  1. Each pod requests 100m and uses 150m: utilization 150%.
  2. 3 pods carry 450m in total. At the 50% target a pod should use 50m.
  3. 450m ÷ 50m = 9 pods, the same as 3 × 150 ÷ 50. ceil rounds up, then maxReplicas: 6 caps it.
  4. 15 s later: 450m over 6 pods is 75%, still above 50%, so it stays at 6.
  • Utilization is relative to the request, not the limit. No CPU request, no autoscaling.
  • In the lab it went from 2 to 6 pods in about 30 seconds.
  • Observed on kind: CPU went up to 467% of the request before the new pods came up, then scaled back to 2 about a minute after the load stopped with a 30 s window.

Jobs and CronJobs

Jobs: run once, then stop

apiVersion: batch/v1
kind: Job
metadata:
  name: migrate
spec:
  backoffLimit: 3
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: ghcr.io/amirilovic/k8s-training-app:v1
          args: ["migrate"]
  • A Deployment keeps pods running. A Job runs one to completion and retries on failure.
  • Same image as the app, different argument: migrate applies the EF Core migrations and exits.
  • A finished Job is never run again. Its pod stays as Completed, so you can read the log.

Job settings

restartPolicyNever: each retry is a new pod. OnFailure: the same pod restarts its container.
backoffLimitRetries before the Job counts as failed. Default 6, with growing waits between tries.
completionsHow many successful pods finish the Job. Default 1.
parallelismHow many pods run at the same time. Default 1.
activeDeadlineSecondsFail the Job when it runs longer than this, whatever retries are left.
ttlSecondsAfterFinishedDelete the Job and its pods this long after it finishes.
  • Lab 8 shows backoffLimit (a Job that fails three times and gives up) and completions with parallelism (6 runs, 2 at a time). The deadline and the TTL are "Finished early?" extras.
  • Make a Job safe to run twice: a retry after a timeout or a node failure may repeat work that half succeeded.

CronJobs: a Job on a schedule

apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-report
spec:
  schedule: "0 2 * * *"      # 02:00 every day
  timeZone: Europe/Berlin
  concurrencyPolicy: Forbid
  jobTemplate:               # a whole Job spec
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: report
              image: myapp:v1
              args: ["report"]
  • schedule is cron syntax: minute, hour, day of month, month, day of week. UTC unless you set timeZone.
  • concurrencyPolicy: let runs overlap, skip the new one (Forbid), or replace the old one.
  • suspend: true pauses it. kubectl create job --from=cronjob/… runs it now.
  • It keeps the last 3 successful and the last failed Job (successfulJobsHistoryLimit, failedJobsHistoryLimit), so old runs clean themselves up.
  • A CronJob replaces cron on a VM or a scheduled task in Windows: it runs on any node, and its logs and history are in the cluster.

Volumes and databases

A container's files die with it

  • The writable layer from Monday is deleted with the pod. A restarted Postgres would start empty.
  • A volume is a folder mounted into the container that lives outside it.
  • You have used two kinds already: configMap and secret.
VolumeLives as long as
emptyDirthe pod
configMap, secretthe object
persistentVolumeClaimuntil you delete the claim

Asking for disk

PersistentVolumeClaim"1Gi, ReadWriteOnce"
→
StorageClass standardknows how to make disks
→
PersistentVolumethe actual disk
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 1Gi
  • You ask for a size. The StorageClass creates the disk.
  • On kind it is a folder on a node. On AWS the same YAML gets an EBS volume.
  • ReadWriteOnce: one node at a time.

Databases in Kubernetes

In production

Your database is a managed service (RDS, Azure SQL). The app gets its connection string from a Secret. Nothing else changes for you.

StatefulSets run clustered databases inside Kubernetes. That is platform work, and out of scope.

In Lab 9

kind: Deployment
spec:
  replicas: 1
  strategy:
    type: Recreate

Recreate stops the old pod before it starts the new one. The default rolling update does it the other way round, so for a moment two Postgres pods would write to the same data folder. The cost is a few seconds of downtime on every change.

RBAC: who may do what

kind: Role                 # what: verbs on resources
metadata:
  name: pod-reader
  namespace: payments
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
---
kind: RoleBinding          # who gets it
metadata:
  name: devs-read-pods
  namespace: payments
subjects:
  - kind: Group
    name: payments-devs
roleRef:
  kind: Role
  name: pod-reader
  • A Role lists what may be done in one namespace. A RoleBinding gives it to users, groups or a pod's ServiceAccount.
  • ClusterRole and ClusterRoleBinding do the same for the whole cluster.
kubectl auth can-i list pods -n payments
kubectl auth can-i --list -n payments
  • The error they will meet: Error from server (Forbidden): pods is forbidden: User "anna@example.com" cannot list resource "pods" in API group "" in the namespace "training". Real output from kind with --as=anna@example.com.
  • Our kind cluster gives everyone full admin, so nothing in the labs was ever forbidden. Real clusters are not like that.
  • Pods have identities too: each runs as a ServiceAccount, and RBAC decides what the app may do if it calls the Kubernetes API.
  • apiVersion rbac.authorization.k8s.io/v1 and the apiGroup lines are left out of the slide to save space.

How a user gets a role

you log incertificate, Entra ID, AWS IAM
→
API serveruser + groups
→
RoleBindingnames the user or group
→
Roleallowed verbs
kubectl auth whoami
Username   kubernetes-admin
Groups     [kubeadm:cluster-admins
            system:authenticated]

kubectl get clusterrolebinding \
  kubeadm:cluster-admins -o wide
ROLE                        GROUPS
ClusterRole/cluster-admin   kubeadm:cluster-admins
  • Kubernetes stores no users. Your name and groups come from how you log in.
  • Bind roles to groups. Joining a team in the identity provider then gives the access.
  • Pods log in too, as their ServiceAccount, and get roles the same way.
  • The output is from our kind cluster. The kubeconfig holds a client certificate with CN=kubernetes-admin (the user) and O=kubeadm:cluster-admins (the group). A ClusterRoleBinding gives that group the cluster-admin ClusterRole, which is why nothing was ever forbidden in the labs.
  • Ways to log in: a client certificate (kind, kubeadm), an OIDC token from the company's identity provider such as Entra ID or Okta, which carries a groups claim, or the cloud's IAM. On EKS, access entries map an IAM role to Kubernetes groups; on AKS, Entra ID groups are used directly.
  • The group name in a RoleBinding must match exactly what the identity provider sends.
  • A pod's identity is system:serviceaccount:<namespace>:<name>. A RoleBinding can name it as kind: ServiceAccount.
