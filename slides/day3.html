Requests and limits

Requests and limits

resources:
  requests:          # reserved, used for scheduling
    cpu: 100m        # 0.1 of a core
    memory: 128Mi
  limits:            # hard ceiling
    cpu: "1"
    memory: 256Mi
Over the limitWhat happens
CPUthrottled, gets slower
memorykilled: OOMKilled exit 137
request too big for any nodePending forever

.NET reads the limits

Container setting.NET sees
CPU limit 1Environment.ProcessorCount = 1
memory limit 128MiGC heap limit 96 MB (75%)

/admin/leak?managed=true fills byte[] until .NET throws OutOfMemoryException. The container survives.

/admin/leak fills native memory, which the GC does not limit. Linux kills the container: OOMKilled

Thread pool and Server GC size themselves from ProcessorCount, so a CPU limit changes how your app behaves under load.

  • Numbers from /api/info on kind with a 128Mi limit and a CPU limit of 1.
  • Native leaks in real apps: unmanaged libraries, image processing, large pinned buffers.

Autoscaling

The HorizontalPodAutoscaler

kubeletmeasures pods
→
metrics-serverkubectl top
→
HPAevery 15 s
→
Deploymentreplicas: 2 … 6
  • The HPA only changes one number: the Deployment's replicas.
  • It adds pods, not nodes. When nodes are full, new pods stay Pending. The cluster autoscaler adds nodes, and that is a platform job.

How it decides

utilization = CPU used ÷ CPU request

desired = ceil( current × utilization ÷ target )

3 pods at 150% with a 50% target: 3 × 150 ÷ 50 = 9, capped at maxReplicas: 6.

  • Utilization is relative to the request, not the limit. No CPU request, no autoscaling.
  • Scaling up is fast. Scaling down waits 5 minutes by default, so a short dip does not remove pods.
  • In the lab it went from 2 to 6 pods in about 30 seconds.
  • Observed on kind: CPU went up to 467% of the request before the new pods came up, then scaled back to 2 about a minute after the load stopped with a 30 s window.

An HPA in YAML

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 2
  maxReplicas: 6
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 50 }
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 30
  • Remove replicas from the Deployment once an HPA owns it, or every apply resets the count.
  • The 30-second window is for the lab, so you see it scale down within the lab.

Storage and databases

A container's files die with it

  • The writable layer from Monday is deleted with the pod. A restarted Postgres would start empty.
  • A volume is a folder mounted into the container that lives outside it.
  • You have used two kinds already: configMap and secret.
VolumeLives as long as
emptyDirthe pod
configMap, secretthe object
persistentVolumeClaimuntil you delete the claim

Asking for disk

PersistentVolumeClaim"1Gi, ReadWriteOnce"
→
StorageClass standardknows how to make disks
→
PersistentVolumethe actual disk
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 1Gi
  • You ask for a size. The StorageClass creates the disk.
  • On kind it is a folder on a node. On AWS the same YAML gets an EBS volume.
  • ReadWriteOnce: one node at a time.

Databases in Kubernetes

In production

Your database is a managed service (RDS, Azure SQL). The app gets its connection string from a Secret. Nothing else changes for you.

StatefulSets run clustered databases inside Kubernetes. That is platform work, and out of scope.

In Lab 9

kind: Deployment
spec:
  replicas: 1
  strategy:
    type: Recreate

One replica and Recreate, so two Postgres pods never share the data folder.

Jobs: run once, then stop

apiVersion: batch/v1
kind: Job
metadata:
  name: migrate
spec:
  backoffLimit: 3
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: ghcr.io/amirilovic/k8s-training-app:v1
          args: ["migrate"]
  • A Deployment keeps pods running. A Job runs one to completion and retries on failure.
  • Same image as the app, different argument: migrate applies the EF Core migrations and exits.
  • A CronJob creates a Job on a schedule.

Helm

A chart is templates plus values

templates/deployment.yaml, service.yaml, …
values-prod.yamlreplicas: 3, host: prod.localhost
→
helm installrenders
→
release "web"plain Kubernetes objects
spec:
  replicas: {{ .Values.replicas }}
  template:
    spec:
      containers:
        - name: web
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
  • One chart, many environments: only the values file changes.
  • Helm remembers every release, so helm rollback works like rollout undo, for everything at once.

Helm commands

helm repo add traefik https://traefik.github.io/charts
helm template traefik traefik/traefik --version 41.6.1 \
  -n traefik -f setup/traefik-values.yaml

helm install web ./web -n web-dev --create-namespace \
  -f web/values-dev.yaml
helm upgrade web ./web -n web-dev -f web/values-dev.yaml \
  --set image.tag=v2
helm history web -n web-dev
helm rollback web 1 -n web-dev
  • Tuesday's setup/traefik.yaml is the Traefik chart, rendered with helm template.
  • Always pin --version.
  • helm template prints the YAML without installing. Use it when a template does not do what you expect.
